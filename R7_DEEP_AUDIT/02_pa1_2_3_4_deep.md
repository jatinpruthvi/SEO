# DEEP PHASE A AUDIT — Hidden Issues & Cross-File Conflicts

## PHO-001: Intl.DateTimeFormat timezone honor (lines 2947-2987)

### Code path
```javascript
Intl.DateTimeFormat.prototype.format = function(date) {
    const opts = this.resolvedOptions();  // ← recursion risk
    const effectiveTz = (opts && opts.timeZone) ? opts.timeZone : tz;
    const f = new Intl.DateTimeFormat("en-US", { timeZone: effectiveTz, ... });
    return f.format(date);
};
```

### 🚨 HIDDEN ISSUE A1.1: Recursion in resolvedOptions()
The override creates a function that calls `this.resolvedOptions()`. But `Intl.DateTimeFormat.prototype.resolvedOptions` is ALSO overridden (line 2940-ish) to return options with `timeZone: tz`. This means:

1. Page calls `dtf.format(date)` 
2. Our format() calls `this.resolvedOptions()`
3. Our resolvedOptions() returns `{ timeZone: tz, locale: "en-US", ... }`
4. We use `opts.timeZone` from #3 (which is `tz` - persona's TZ)
5. We create a new `Intl.DateTimeFormat("en-US", { timeZone: effectiveTz, ... })` 
6. Call `f.format(date)` on the **NEW** Intl.DateTimeFormat
7. Since `f` is a fresh instance, its `format` is the **OVERRIDDEN** one (prototype method)
8. f.format calls `this.resolvedOptions()` — on the NEW instance — calls our resolvedOptions
9. New instance's `this` doesn't have a timeZone, so it returns `tz` again
10. This loops and creates infinite IntlDateTimeFormat objects (stack overflow risk)

Wait — actually let me re-read. The format() we override is on the **prototype**. So:
- Page makes dtf = new Intl.DateTimeFormat({timeZone: 'LA'})
- dtf's prototype is Intl.DateTimeFormat.prototype
- dtf.format(date) → our format (prototype-level)
- this.resolvedOptions() → calls our resolvedOptions on **this dtf** (which has timeZone='LA')
- Our resolvedOptions FORCES `options.timeZone = tz` — **OVERWRITES the caller's LA!**

🚨 **CRITICAL BUG**: The `Intl.DateTimeFormat.prototype.resolvedOptions` override (line 2942) **destroys the PHO-001 fix**! It forces `timeZone = tz` (persona's TZ) and `locale = "en-US"` regardless of what the caller passed.

Page does:
```js
new Intl.DateTimeFormat('en-US', { timeZone: 'America/Los_Angeles' }).format(new Date())
```

What happens:
1. `dtf = new Intl.DateTimeFormat('en-US', { timeZone: 'LA' })` — this works
2. `dtf.format(new Date())` — calls our override
3. `this.resolvedOptions()` — calls our override, which **forces** `timeZone = tz` (e.g., NY)
4. `effectiveTz = opts.timeZone = tz` (NY) — PHO-001 fix says "honor caller's", but caller was LA!
5. `f = new Intl.DateTimeFormat("en-US", { timeZone: effectiveTz })` — creates with NY
6. `f.format(date)` returns NY time

The result: the page gets NY time when it asked for LA. **PHO-001 fix is broken!**

**Root cause**: `Intl.DateTimeFormat.prototype.resolvedOptions` override on line ~2942 should NOT force the `timeZone` field when the caller specified one.

**Fix**: Change line 2942 from:
```js
options.timeZone = tz;        // ← always forces
options.locale = "en-US";    // ← always forces
```
to:
```js
if (!options.timeZone) options.timeZone = tz;
if (!options.locale) options.locale = "en-US";
```

Or just remove the resolvedOptions override entirely (let native handle it) and only override `format` and `formatToParts`.

### 🚨 HIDDEN ISSUE A1.2: This leak affects IFRAME context too
The `__sreApplyFingerprinting` function (line 1380+) overrides `Intl.DateTimeFormat.prototype.resolvedOptions` in the iframe, with the same broken logic.

### Severity: 🚨 SYSTEM-BREAKING
- The PHO-001 fix is functionally broken — pages asking for specific timezones get the persona's TZ instead
- This is the most critical Phase A issue that wasn't caught before

## PHO-002: chrome.app.runningState stateful

### Code path (lines 685-730)
```javascript
const runningStateMock = function() {
    if (Math.random() < 0.30) {
        const cycle = ["cannot_run", "ready_to_run", "running"];
        _currentRsState = cycle[Math.floor(Math.random() * 3)];
    }
    return _currentRsState;
};
```

### 🚨 HIDDEN ISSUE A2.1: Math.random() breaks per-persona determinism
The audit comment says "R7-PHO-002: Complete chrome.app mock with stateful runningState" but the actual implementation uses `Math.random()` (NOT seeded). Two launches of the same persona produce different rotation patterns. This violates the "per-persona determinism" guarantee.

Also affects `csiMock` — wait, no, csi uses `seededRandom()`. Let me check csi again.

Actually `csiMock` uses `seededRandom()` and caches the result. Good. But `runningState` uses unseeded Math.random(). Inconsistent.

### 🚨 HIDDEN ISSUE A2.2: install() returns Promise.resolve() instead of actual state
The `installMock = function() { return Promise.resolve(); }` — real Chrome's `chrome.app.install()` returns `Promise<boolean>` indicating success. A page doing `const success = await chrome.app.install();` gets `undefined` which is falsy. The page thinks the install failed. If the page has a flow that depends on install() returning true, that flow is broken.

This isn't critical for stealth (most pages don't call install()), but it IS a functional break.

### Severity: LOW (doesn't break system, breaks per-persona determinism)

## HOR-001: Defensive userAgent parsing

### Code path (hardened_orchestrator.py)
```python
def _safe_parse_user_agent(fp):
    default_full = "120.0.6099.109"
    default_major = 120
    ...
```

### ✅ Looking at the actual orchestrator code
- Good: handles None, empty, non-string, missing 'navigator', missing 'userAgent'
- Good: catches ValueError, TypeError, IndexError
- ✅ Already verified in previous audit

### 🚨 HIDDEN ISSUE HOR-1.1: uaFullVersion for Firefox personas
When FP_CONFIG is "Firefox" (no Chrome/), `_safe_parse_user_agent` returns the Chrome 120 default. The JS side checks `isFirefox` and would not set chrome.app. But `uaFullVersion` is still "120.0.6099.109" in the FP_CONFIG. The fingerprint JSON has `userAgent: "Firefox/..."` but `uaFullVersion: "120.0.6099.109"`. A fingerprinting grid could detect this inconsistency.

In the JS code, when isFirefox is true, the `chrome` window property is deleted via `safeDelete(window, 'chrome')`. So navigator.userAgent is Firefox but `uaFullVersion` and `uaMajor` are Chrome 120. That's a fingerprint inconsistency.

**Recommended fix**: When persona is Firefox, uaFullVersion/uaMajor should be empty or undefined in FP_CONFIG.

### Severity: MEDIUM (creates a detectable inconsistency)

## HOR-002: Async panic cleanup in thread

### Code path (lines 765-870)
```python
def _panic_handler(signum, frame):
    global _panic_triggered
    if _panic_triggered: return
    _panic_triggered = True
    # ... sync tc qdisc cleanup ...
    # Spawn thread to run async cleanup
    cleanup_thread = threading.Thread(...)
    cleanup_thread.start()
    cleanup_thread.join(timeout=3.0)
    os._exit(99)
```

### 🚨 HIDDEN ISSUE HOR-2.1: `_panic_triggered` flag is read by `handle_graceful_shutdown` but not protected by lock
If SIGUSR1 fires in the main thread while `handle_graceful_shutdown` is running in the asyncio loop, there's a race condition. However, Python signal handlers only run in the main thread, and `_panic_triggered` is only set by the handler. The check `if _panic_triggered: return` is the right pattern. ✅ Probably fine.

### 🚨 HIDDEN ISSUE HOR-2.2: Thread.run_until_complete on a new loop
```python
def _async_panic_cleanup():
    try:
        loop = asyncio.new_event_loop()
        asyncio.set_event_loop(loop)
        if db_pool is not None:
            loop.run_until_complete(db_pool.close())
        loop.close()
    except Exception:
        pass
```

Issues:
- `asyncio.set_event_loop(loop)` — sets it globally. If the main thread is also using asyncio, this could conflict on Python 3.10+ where each thread can have its own event loop policy.
- `loop.run_until_complete()` is blocking — fine in a thread.
- `loop.close()` — may not clean up pending tasks. If `db_pool.close()` schedules more tasks, they could be left dangling.

In practice for a 1-persona setup with 1 connection, this is fine. But under load, the cleanup might be incomplete.

### Severity: LOW (acceptable for current scale)
